# 敏感写入的全文索引维护

首次 Windows 完整对照发现，每条敏感转换和已保护记录重复保存都会 rebuild 全库索引。一万条历史下，转换 p95 为 488.87 ms。第一项修复跳过已排除记录的维护，将公开记录转保护后的 rebuild 改为 optimize；第二轮冻结树 `8cdce57cf82f2da25b3af52327032639603b484a` 的完整对照仍显示转换 p95 为 147.79 ms，超过 22.27 ms 的门槛。两轮失败及全部原始样本均保留，不能用少量 SQL 探针替代产品门槛。

optimize 不重新读取历史行分词，却仍合并整个索引的 B-tree，因此不是按记录计费的清理方式。[SQLite 官方说明](https://sqlite.org/fts5.html#the_optimize_command)

## 按记录清理及兼容

schema 20 保留业务字段、正文与附件格式、既有密文和五字段可见性规则，只升级派生搜索索引的清理方式。迁移在一个事务内清理旧索引并启用 FTS5 `secure-delete`；写连接仍启用 `PRAGMA secure_delete=ON`。后续旧词项由触发器在字段变更的同一事务内物理删除，敏感转换不再逐条运行全库 optimize。新保护记录和原本排除的记录仍不入索引。

FTS5 安全删除会将派生索引升级为格式 5，读取该索引至少需要 SQLite 3.42。字段及完整备份的数据格式不变；旧客户端通过 schema 20 的版本门槛拒绝写入。直接使用较旧系统 SQLite 的外部工具不能读格式 5 索引，应使用发行程序或受支持工具；不能为兼容外部工具而关闭安全删除。[FTS5 secure-delete 的语义和兼容边界](https://sqlite.org/fts5.html#the_secure_delete_configuration_option)

产品固定使用 rusqlite 上游提交 `661107f6eb5d7477c61be1221744de3ad96c53e7` 及其 SQLite **3.54.0** amalgamation，源标识为 `2026-10-09 15:46:58 be8d059e9a49089ab2dce5ed26dd87aaf598fdc5fbe0b107c0dd758464bcd5e3`。已发布 Rust crate 的版本号不能替代对实际 SQLite 源码的核对：调查时最新发布 crate 仍携带 3.53.2；现有 3.45.0 也早于相关索引正确性与损坏输入处理修复。固定提交使依赖可复现，不在构建时跟踪移动分支。[SQLite 3.54.0 发布记录](https://sqlite.org/releaselog/3_54_0.html)、[secure-delete 损坏输入修复](https://sqlite.org/hctree/info/34171bee084f7080)

新版查询规划器还会在 `tags NOT NULL` 的表上化简原清理索引中的 NULL 分支，使强制使用该 partial index 的旧查询报错。schema 20 在同一迁移事务内将索引和两处清理查询统一为 `is_pinned=0 AND COALESCE(tags,'[]')='[]'`，保留旧库 nullable tags 的含义；不修改历史 tags，也不以移除索引强制或全表扫描绕过兼容问题。

## 原子性和验证

转换、索引删除、标签写入与提交仍处于原 Immediate 事务或嵌套 savepoint。索引失败、后续 SQL 失败或提交失败均回滚字段、标签和索引，不在返回成功后异步补清理。启动历史对齐保留批末一次 rebuild，用于修复遗留内容，不将历史残留清理伪装为新写入热路径的固定成本。

回归须验证：独有词项在转换前确实存在于影子表、转换后消失；共享公开词项保留；MATCH、fts5vocab 与索引完整性一致；单 segment、多 segment、重复转换、已有旧删除标记、迁移失败、后续标签 SQL 与外层延迟提交失败均保持事务语义。性能结果单独记录在 [性能验收](v0.2-performance-validation.md)，实现路径改变本身不表示门槛通过。

这一清理仅覆盖受管理事务及当前索引，不承诺擦除旧 WAL、备份或文件系统中的历史副本。
