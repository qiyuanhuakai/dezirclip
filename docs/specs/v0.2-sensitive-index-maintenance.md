# 敏感写入的全文索引维护

原实现对每次敏感重复保存、手工标签转换和受保护字段编辑执行全库 FTS rebuild。schema 19 已有过滤视图与 old/new 触发器，因此全库重新读取及分词不应成为每次受保护写入的固定成本。

本次保留 schema、密文和 FTS 格式。SQL 可见性函数与写入计划共用一个五字段规则：原始 tags JSON、content、preview、HTML、OCR。无效 JSON、敏感标签及具有完整历史密文结构的任何字段均不可见；普通文字前缀仍按原规则处理。

可见记录转为保护记录时，仍在原 Immediate 事务或嵌套 savepoint 内完成字段保护、触发器旧词项删除和 FTS5 optimize。仅逻辑删除不足以清理旧 segment；合并配合 SQLite secure_delete 清理当前受管理索引。任何维护或后续标签 SQL/提交失败都回滚整个事务。新保护记录及原本已排除的记录不执行全库维护。启动历史对齐与迁移仍保留一次 rebuild，以修复旧索引，不依赖新热路径来追溯修复历史残留。

optimize 合并已有 b-tree，不重新扫描历史行分词，但仍可能涉及整个索引，不能据此承诺固定耗时。未启用会升级为 FTS 格式 5 的 secure-delete 选项。[SQLite FTS5 说明](https://sqlite.org/fts5.html#the_optimize_command)

回归同时检查独有词项在清理前确实存在于影子表、清理后消失，fts5vocab 与 MATCH 排除受保护行，普通共享词保留，以及 integrity-check 与格式 4。局部失败注入验证零维护分支和清理失败回滚；真实 CaptureEngine/SQLite store 覆盖已加密手工敏感条目的重复捕获；延迟外键失败覆盖外层提交回滚及缓存读回。

1000 行 SQL 因果探针观察到 rebuild 为转换调用可见性函数 1002 次，optimize 为 2 次；该探针不包含系统加密且未控制主机负载，只用于解释执行路径。此前完整正式失败数据保留，最终修复树仍需独立安静窗口重新验证性能门槛。旧 WAL、空闲页、备份及文件系统历史副本仍不在追溯擦除承诺内。
