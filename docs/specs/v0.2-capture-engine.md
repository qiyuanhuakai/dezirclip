# P2-B 捕获边界

捕获业务位于 `crates/dzc-core/src/services/capture/`。Core 不依赖 Tauri、窗口、系统剪贴板 API 或桌面运行时；平台读取和监听位于 `crates/dzc-platform/src/capture/`。桌面的 `services/clipboard` 只负责配置快照、现有处理队列和交互适配。

## 输入、结果与事件

`CaptureContext` 包含来源、捕获时间、设置快照、会话历史引用和顺序粘贴回声。`CaptureReader` 在预判断通过后才读取正文，返回数据和不含正文的指纹元数据。`CaptureEngine::read` 可在监听回调内冻结数据及其来源，再交给现有单个处理 worker；`capture_frame` 再检查当前暂停和来源规则，避免延迟读取下一次剪贴板并误配来源。

结果明确区分 `Stored`、`Skipped`、`Rejected`、`Failed`。成功结果供可信桌面适配层使用，包含条目、被移除的 ID、OCR 目标及隐私决策。`EventSink` 只发送 ID、持久化状态和稳定原因，不含正文、HTML、OCR 或可解密载荷。只有提交成功才发送 Stored、Removed 或 OcrRequested；失败不会启动 OCR 或分发成功条目。

`CaptureStore` 提供 prepare、去重查询、存在性查询和 commit 细接口。Engine 不接收裸连接或缓存。当前 `DbState::capture_store` 是 P2-A 兼容存储的嵌入式适配入口，P2-C 的业务 facade 可在此接口上继续收敛公共面。

## 顺序与既有策略

处理顺序为来源与暂停预判断、按需读取、解析分类、隐私决策、去重、保存和必要衍生结果。文件优先于富文本，富文本优先于普通图片，最后读取文本结果；Windows GIF 原始数据和 RGBA 像素在通过通知过滤后才编码。富文本保留已有图片回退与三次、35ms 间隔的有条件重试：未声明图片时不等待。

未启用富文本时不读取 HTML。Windows 文件捕获关闭时通过格式元数据跳过文件载荷；Linux 保留单个图片文件作为图片捕获的既有行为。正文及 HTML 保持原始空白和换行，只规范化列表摘要；单个文件的图片、视频分类后缀保持不变。

通知状态保留相同 sequence 跳过、500ms 重复事件抑制、相同图片指纹抑制、文件历史被删除后允许再次捕获，以及主/备用指纹与十秒窗口的自身复制抑制。文件重复检查通过存储接口执行。会话项继续使用负 ID，并保证同一毫秒产生的多个新项不会重用 ID；会话去重保留固定、标签和使用计数。

现有隐私设置和匹配表达式保持语义。检测结果先形成 `PrivacyEvidence`，再由同一份 `PrivacyPolicy` 生成 Allow、Encrypt、Skip 或 SessionOnly 决策。来源排除和暂停先于正文读取；配置规则匹配和继承的手动敏感标签形成独立证据。现有 5000 字节检测上限留下 Incomplete 证据，不声称完成扫描；十 MiB 的文本保存上限保持不变。已经受保护的去重目标不能由新捕获的普通标签覆盖。

## 存储与桌面适配

普通 HTML 的附件准备只规划字节和稳定路径。SQLite 适配使用 P0-B 的捕获事务，在当前保护状态复查及字段、标签写入之后才创建附件；提交失败仅清理本次创建的文件。计划错误、附件预算错误、密钥和 SQL 失败均传播为明确结果，不回退到原 HTML 后继续宣称保存成功。会话 HTML 的本地图片继续以内嵌数据保留在内存，读取同样限制单图 16 MiB、累计 32 MiB、64 个引用，并只接受打开后确认的普通文件，避免 FIFO 等特殊文件等待；失败不改变已有会话。已有 OCR 继承沿用 P0-B 的捕获保存契约。

会话历史更新、负 ID 分配和去重属于 Core；窗口可见性、空闲销毁后的 catch-up、前端载荷截短、声音、PasteQueue 和 OCR 运行时任务属于桌面适配。捕获通知使用 `clipboard-captured: {id}`，不广播正文或完整图片；可见客户端通过 `get_captured_entry_summary(id)` 按需读回已提交条目。正 ID 的图片返回存储层规范化后的附件路径；负 ID 从会话读取，内存图片仍可通过显式 invoke 返回完整 data URL 以保持渲染兼容，不声称全部 IPC 零拷贝。文本及 HTML 沿用现有摘要上限，错误只返回固定原因码。旧 `clipboard-updated` 保留给手工编辑等既有调用。隐藏窗口不接收逐条渲染更新，下次显示仍刷新持久历史。捕获失败不会触发队列增长或复制提示音。

Windows 消息窗口、X11 XFixes 及原有轮询后备位于 Platform。回调只接收 `ClipboardChange` 元数据，`run_clipboard_monitor` 是阻塞入口；`listen_clipboard` 仅启动原有一个监听 worker。`probe_clipboard_monitor` 不读取正文、不启动 worker：Windows 实际注册并释放监听窗口；Linux 协商 XFixes 版本及 selection 通知，必要时仅验证轮询连接，返回实际后端。Linux 读取、监听及探测先检查 DISPLAY 是否可用于 X11 TCP 后备端口算术，无设置或溢出范围返回固定错误，不把原始环境内容写进错误。处理 worker 也沿用既有数量，没有 IPC、服务进程或新增默认常驻组件。Linux 保留 `DEZIRCLIP_DISABLE_LINUX_SERVICES` 及旧变量的退出开关。当前接口不声称支持取消或跨进程捕获所有权交接。

## 验证边界

Core 的纯逻辑及真实 SQLite 回归覆盖预判断不读正文、失败不发成功事件、提交后才发事件、会话字段保留、HTML 稳定去重、受保护目标拒绝新资源，以及延迟提交失败清理。Platform 保留图片重试、CF_HTML 字节偏移、Windows DIB 和 X11 文件格式回归。

```text
cargo test -p dzc-core -p dzc-platform --lib --locked
cargo check --workspace --all-targets --locked
```

真实 X11 读取应在私有 Xvfb/DBus 会话内显式设置 `DEZIRCLIP_RUN_LINUX_CLIPBOARD_SMOKE_TESTS=1`，测试原始文本、HTML 和文件优先级，不连接日常桌面的剪贴板。Xvfb 使用 `-noreset`，避免短连接探测之间最后一个客户端离开导致测试服务器重置、短暂退回轮询；该模式模拟持续存在的桌面 X server。默认纯测试通过不能替代该原生验收。Windows 完整已安装程序升级、WebView 交互及不同用户会话不是这些 Core/Platform 回归的证明范围。

性能测量需区分 Core 捕获、平台读取和已有 CLI 冷启动指标，按普通、重复和敏感路径记录；参见 [同环境性能验证](./v0.2-performance-validation.md)。旧 AppHandle 流水线不能仅凭新的 headless 入口伪造同口径的重构前采样。
