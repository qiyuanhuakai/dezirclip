# Phase 4-B protected resources

This progress extends the Phase 4-A persistent privacy state and original capture tickets. It requires the matching Phase 4-C frontend before release: history resources are now read by record ID and epoch, and the broad Tauri asset protocol is disabled. Feedback, reversible exact exceptions and source-policy management are a separate subsequent progress; this document does not declare all Privacy 2.0 complete.

## Persistent representation

Schema 23 rejects older writers through the existing schema guard. Its visibility-transition trigger advances the shared privacy epoch when any of the tags, content, preview, HTML or OCR fields changes between public and protected. The trigger and schema marker are migrated in the same transaction. Ordinary body text resembling an encryption prefix retains its existing compatibility behavior; valid historical ciphertext remains protected even without a sensitive tag.

Sensitive images become complete RAM data URLs before encryption. Supported HTML image references become complete embedded RAM data URLs before encryption. Files and videos become a versioned `dzc-files-v1:` JSON archive containing safe basenames and complete base64 bytes; the complete archive is encrypted using the existing protected-field envelope. No new cipher or key store is introduced. Protected saves and conversions do not create plaintext managed attachments. The bounds are 16 MiB per resource, 32 MiB in total and 64 resources. Unsupported, missing, oversized or unresolved resources fail closed without returning their original contents in errors.

Existing managed plaintext files are removed after a successful conversion only when no surviving record references them. User originals and shared resources are retained. This does not promise forensic removal of old WAL pages, user files, shared public records or pre-existing backups. A post-commit cleanup error is reported explicitly; the committed protected record remains protected.

OCR retains the original capture ticket through queueing, recognition and the final repository transaction. Protected OCR is encrypted with the other protected fields, never indexed by the managed FTS view, and a failed status write rolls back all field, revision and epoch changes. OCR notifications contain metadata and no recognized text. Generated transformations identify their source record and preserve its protection even when the derived text no longer matches a detector.

## Reads, exports and native consumers

The normal GUI projection appends a sensitive marker to protected placeholders without modifying user tags, and clears body, preview, HTML, OCR and source paths. This includes historical untagged ciphertext and negative session IDs. An explicit, epoch-bound reveal may obtain complete image/HTML RAM content. File/video reveal returns basenames only, never the archive or a local filesystem URL. Normal thumbnails are bounded and fetched through the record ID and epoch. Backgrounds and managed Emoji use their separate bounded user-resource getters.

Native selected-copy and external-open operations obtain opaque Core authorization. Protected clipboard representations carry native exclusion metadata in the same offer. Copying a derived protected text uses the original source ID and epoch, and its explicit persistence keeps the sensitive marker. Native consumers do not obtain the master key.

Linux file export uses sealed anonymous memfd handles for clipboard delivery and writable anonymous handles for an explicitly opened editor. Each export has a separate native owner descriptor table; URIs use that owner's process ID, not the long-lived Host or `/proc/self`. Its files remain empty until the parent confirms this PID has never identified a previous export in the same Host lifetime. Revocation confirms the original process's exit through a pidfd before acknowledging success. Missing kernel support fails closed. A standalone clipboard child additionally checks the read-only database UUID/epoch lease and never gains decryption permission. Linux native consumers may display an FD number instead of the archived basename. These proc URIs are temporary OS references, not durable identifiers across Host restarts and eventual OS PID reuse. Consumers that cannot open a proc FD are unsupported; no plaintext disk fallback is used.

Windows native export uses an owner-only protected directory, a separate protected subdirectory for each archive member, and kernel delete-on-close handles. Equal or case-equivalent basenames therefore preserve the complete original member list. These are short-lived plaintext files supplied only after native authorization, not persistent history attachments. A standard independent reader is supported. Revocation prevents a new reader from opening the name; already opened handles may finish reading. The kernel deletes the file after the final reader closes, including process-exit cleanup of the owner handle. No claim is made that already disclosed bytes can be recalled.

The native lease is bounded to five minutes and rechecks the original authorization. The owner synchronously revokes exports before acknowledging a privacy mutation. An unconfirmed native-owner stop returns an error and retains its handle for retry. Clipboard replacement closes previous clipboard exports without cancelling an unrelated authorized external editor. Explicit privacy revocation closes both classes. External-editor monitoring owns the original lease and reads its bound file handle; it never reopens an old URI. Revocation or expiry stops monitoring. Writes use the original capture ticket; an on/off cycle cancels late edits instead of obtaining a new ticket.

## Backups and compatibility

Version `dezirclip-export-v2` preserves complete protected resource bytes in the existing authenticated encrypted backup format. Protected records require a passphrase for export; raw plaintext JSON serialization also rejects sensitive entries and protected file archives. The v1 DezirClip and legacy TieZ JSON formats remain importable. Replace and Merge hold the original request ticket across file reading, decryption and resource validation, then check it inside the final transaction. A stale import cannot clear or partially replace current history. Import while a privacy session is active is rejected unless a future explicit manual-confirmation business API authorizes it.

Validation uses disposable synthetic databases, files and private clipboard namespaces. Core AEAD tests, native Windows DPAPI/export tests and independent-reader kernel tests are distinct evidence. No performance result is claimed by this progress.
