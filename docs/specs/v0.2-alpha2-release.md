## 发布验收文件

验收清单须包含 `schema_version: 1`、`status: "passed"`、`version: "0.2.0-alpha.2"`、完整 40 位 `source_revision`、数字 `release_id`，以及八个实际 NSIS/AppImage 安装包及其签名的 `signed_assets`。每项资产包含 `name`、`id`、`size`、`updated_at`、64 位小写 `sha256`；必须与重新下载并验签的公开资产逐项一致，不能只核对版本号。

清单的 `gates` 是以下四个引用；示例中的哈希占位文字必须替换为对应报告原始字节的实际 SHA-256：

```json
{
  "public_assets": { "file": "public-assets.json", "sha256": "<64位小写SHA-256>" },
  "appimage_updates": { "file": "appimage-updates.json", "sha256": "<64位小写SHA-256>" },
  "windows_upgrade": { "file": "windows-upgrade.json", "sha256": "<64位小写SHA-256>" },
  "performance": { "file": "performance.json", "sha256": "<64位小写SHA-256>" }
}
```

四份报告各自包含 `schema_version: 1`、`status: "passed"`、与引用键相同的 `kind`，以及与清单完全相同的 `version`、`source_revision`、`release_id`、`signed_assets`。每份报告的 `checks` 为非空数组，各项都有具体的非空 `name` 和 `status: "passed"`；任一失败、运行中或缺失状态都会拒绝推进。

| `kind` | 可信维护者汇总前必须实际完成的内容 |
|---|---|
| `public_assets` | 公开资产下载、签名及校验和、组件构建身份和 Linux 包元数据 |
| `appimage_updates` | 分别从 0.1.20 和已发布的 0.2.0-alpha.1 进行真实更新，并覆盖签名拒绝与数据保留 |
| `windows_upgrade` | 冻结提交的五组一次性 Windows 安装、更新及卸载场景，包含已发布 alpha.1 升级 |
| `performance` | 最终干净提交与 alpha.1 的同编译器正式采样、性能比较及 Service 空闲资源门槛；功能检查不能代替 |

清单及报告均须为非空且不超过 8 MiB 的普通文件，禁止符号链接。`file` 只能是清单同目录的 ASCII 文件名：字母或数字开头，其余为字母、数字、点、下划线或连字符，以 `.json` 结尾。不允许子目录、绝对路径、盘符、反斜线或文件流；报告位置不以运行命令时的当前目录为准。脚本对同一份有界读取的字节计算哈希并解析 JSON；缺失、内容变化或发布身份不符时，在查询或修改通道前失败。

这是一份由可信维护者依据真实子报告整理的发布汇总格式。脚本检查文件内容与当前发布的绑定关系，不自动运行原生验收，也不认证报告作者或执行事实。维护者应在报告中保留子报告路径和原始哈希，将具体已完成的检查写入 `checks`；不得重新标记旧源码凭据、将失败改为通过，或将现有原生报告中的 `result` 字段直接当作本格式。来源或资产变化后必须重新验收。该汇总无需新增签名私钥或发布权限。
