所有本地 Linux 原生验证均使用独立 HOME、用户/PID/网络/IPC 命名空间、DBus 和私有 Xvfb 或无显示器合成器。功能凭据不等同于正式性能样本，也不证明物理桌面的 Portal 授权界面。Windows 本机不访问用户剪贴板、历史或安装配置；原生安装和系统剪贴板验证在一次性 CI 环境运行。

Linux 最终身份采集器在只读挂载工具目录前先独占创建 WebKitWebDriver 文件挂载点，避免 standalone 和四种 Linux 包共同入口在执行程序前因只读目录而失败。现有 Linux backend CI 单独安装 bubblewrap 并强制运行真实挂载负控/正控，核对缺少挂载点时失败、预建后成功、工具树仍只读、六个命名空间不同及三种凭据系统调用均被拒绝；缺少 bubblewrap 不能跳过该门禁。本地另以实际 master `ef8bf302` 三个 release 程序制作的 QA tar.gz 和 Deb 完成实际 CLI/Service 身份及 Desktop WebView 身份调用，并通过私有 Secret Service 预置和重复预置拒绝。QA 容器不是最终签名发行包，十四份最终资产和三十四份身份仍须在 tag 的原生发行门禁逐一验收。

首次新增的 Ubuntu 24 CI 挂载检查在 loopback 初始化报 `Failed RTM_NEWADDR: Operation not permitted`，尚未执行到文件挂载。按 [Ubuntu 24 用户命名空间前置要求](https://documentation.ubuntu.com/release-notes/24.04/#unprivileged-user-namespace-restrictions)，backend 和最终身份采集 workflow 仅在一次性 GitHub 托管 Linux runner、且相关 AppArmor sysctl 键存在时配置该前置并核对原值及回读；本机和自托管环境拒绝执行配置。网络命名空间、NoNewPrivs 和凭据 syscall 拒绝保持原样，不能以跳过挂载检查替代该前置；首次失败保留在原提交的 CI 记录中。

backend 在本次专用 RUNNER_TEMP 文件中保留原值及回读，绑定 run、attempt、job、source 和 runner 身份。真实挂载步骤位于 backend 最后，先校验原收据并只读复核当前值，再执行原生正负控，使有限日志读取仍能取得实际边界输出；该末尾步骤不再修改 sysctl，缺失、超限或不匹配的收据不能放行。

最终运行时要求数据库结构为 24、线协议为 1.0；桌面和 CLI 的实际链接清单为 Core、Platform、Protocol、Host，Service 额外包含 Service。组件版本和来源提交必须与最终发布提交一致，不能只修改显示文字或重新标记旧二进制。

Stable 保持现有稳定版本。只有公开发布资产验收完成后才推进 Preview 更新清单。

发布工作流仅运行 `node scripts/updater-release.mjs publish-only v0.2.0-alpha.2`：验证四个平台签名后公开版本，保持更新渠道不变。公开资产、两个真实旧版 AppImage 更新、Windows 升级及正式性能验收完成后，执行 `node scripts/updater-release.mjs promote v0.2.0-alpha.2 ACCEPTANCE.json`。该命令接受真实验收清单的文件路径，先读取并验证同目录的四份报告，再重新下载公开制品并验签；不复用草稿时的检查结果。

## 草稿读取失败与受限恢复

原始 [Release 运行的第二次尝试](https://github.com/qiyuanhuakai/dezirclip/actions/runs/39984241118/attempts/2) 中，Windows 升级输入准备及四个架构的身份准备均在读取原草稿 `422045565` 时收到 HTTP 403。此前 ARM64 Flatpak 的 Xvfb 启动失败与这五项权限失败分别保留；不能将重跑后 Flatpak 通过视为后续发行门禁通过。

草稿下载需要调用链允许相应 job 使用 `contents: write`。Windows 工作流仅将该权限授予纯输入准备 job，执行安装器及聚合报告的 job 保持只读；身份采集当前包含实际草稿下载，其 native job 获得相应权限，聚合仍只读。两个 reusable workflow 的调用方也必须允许该权限。下载步骤的 token 不写入产物、策略、诊断或执行产品的环境，正常 tag 流程的源码与签名断言继续生效。

这五项原失败均发生在成功输出目录创建之前，原来的 `always` 上传因无文件而无法保留诊断。准备过程现在先保存独立、有界的启动诊断，原步骤结束后才为尚未创建的输出目录补入失败诊断，再沿用原 artifact 名称及成功布局上传。失败诊断不包含伪造的 BuildInfo 或通过状态。不得提前创建原采集器或签名准备器要求不存在的输出目录。

修复合入后，旧 run 的 rerun 仍使用原 tag 提交的工作流，不能采用后来合入的权限和诊断修复。同版本恢复通过 `master` 上的 Release 手动入口进行，保留 `v0.2.0-alpha.2` 指向的产品提交 `037f40cf014cd4bb3dce4a0a0c5cbcaee23affae`、原草稿和现有签名资产，不移动标签、重新构建或替换这些产品字节。

恢复上下文必须显式设置 `DZC_RELEASE_RECOVERY=1`，并以 `DZC_RELEASE_TOOLING_SOURCE` 记录真实工具提交。`release_recovery.py` 核对真实 `workflow_dispatch`、`refs/heads/master`、本仓库 `.github/workflows/release.yml@refs/heads/master`、实际 run/attempt、`GITHUB_SHA` 及干净工具 checkout；本地原 tag 必须仍解析为上述产品提交，并是工具提交的祖先。两提交间只允许 guard 中固定列出的 CI、验收工具及本文变化，拒绝产品代码、Cargo 配置、Tauri 配置、未列出的脚本、符号链接或子模块变化。提供的 release ID 必须仍为原草稿。

恢复收据分别记录 `source_revision`（原产品提交）与 `workflow_source_revision`（实际工具提交），job 身份按真实工具提交查找。各程序的实际 BuildInfo、十四份包的原始字节、三十四份角色身份、Windows 升级断言与八份签名资产仍严格绑定原产品提交及草稿。收取与公开验收必须核对这两种真实来源，不得将 `GITHUB_SHA` 或 job 的来源改写为产品提交，也不得把旧失败标为通过。普通 tag 运行继续要求工具、checkout、`GITHUB_SHA` 与产品来源相同。

恢复路径仍等待完整的原生身份和 Windows 安装升级门禁，再执行 `publish-only`。公开资产、两条旧版 AppImage 更新及四份实际发布验收报告完成后才可推进 Preview；Stable 保持原状。

第一次实际恢复运行 [40074429623](https://github.com/qiyuanhuakai/dezirclip/actions/runs/40074429623) 使用工具提交 `5a0124ce330d91928515a48a218eb9f671f2e014`。草稿读取和八份 Windows 升级输入验签已通过，原 HTTP 403 阻断已解除；该运行整体失败，未发布草稿。Windows 升级控制器在启动前将 PATH 中两个 Node 路径拼接成一个文件名，两条场景均未启动安装器。控制器现只选取 PATH 中第一个现存绝对应用路径，合成回归仅提取该函数，不执行占位程序或整个安装脚本。

## 发布验收文件

验收清单须包含 `schema_version: 1`、`status: "passed"`、`version: "0.2.0-alpha.2"`、完整 40 位 `source_revision`、数字 `release_id`，以及八个实际 NSIS/AppImage 安装包及其签名的 `signed_assets`。每项资产包含 `name`、`id`、`size`、`updated_at`、64 位小写 `sha256`；必须与重新下载并验签的公开资产逐项一致，不能只核对版本号。

清单的 `gates` 是以下四个引用；示例中的哈希占位文字必须替换为对应报告原始字节的实际 SHA-256：

```json
{
  "public_assets": { "file": "public-assets.json", "sha256": "<64位小写SHA-256>" },
  "appimage_updates": { "file": "appimage-updates.json", "sha256": "<64位小写SHA-256>" },
  "windows_upgrade": { "file": "windows-upgrade.json", "sha256": "<64位小写SHA-256>" },
  "performance": { "file": "performance.json", "sha256": "<64位小写SHA-256>" }
}
```

四份报告各自包含 `schema_version: 1`、`status: "passed"`、与引用键相同的 `kind`，以及与清单完全相同的 `version`、`source_revision`、`release_id`、`signed_assets`。每份报告的 `checks` 为非空数组，各项都有具体的非空 `name` 和 `status: "passed"`；任一失败、运行中或缺失状态都会拒绝推进。

| `kind` | 可信维护者汇总前必须实际完成的内容 |
|---|---|
| `public_assets` | 公开资产下载、签名及校验和、组件构建身份和 Linux 包元数据 |
| `appimage_updates` | 分别从 0.1.20 和已发布的 0.2.0-alpha.1 进行真实更新，并覆盖签名拒绝与数据保留 |
| `windows_upgrade` | 冻结提交的五组一次性 Windows 安装、更新及卸载场景，包含已发布 alpha.1 升级 |
| `performance` | 最终干净提交与 alpha.1 的同编译器正式采样、性能比较及 Service 空闲资源门槛；功能检查不能代替 |

清单及报告均须为非空且不超过 8 MiB 的普通文件，禁止符号链接。`file` 只能是清单同目录的 ASCII 文件名：字母或数字开头，其余为字母、数字、点、下划线或连字符，以 `.json` 结尾。不允许子目录、绝对路径、盘符、反斜线或文件流；报告位置不以运行命令时的当前目录为准。脚本对同一份有界读取的字节计算哈希并解析 JSON；缺失、内容变化或发布身份不符时，在查询或修改通道前失败。
