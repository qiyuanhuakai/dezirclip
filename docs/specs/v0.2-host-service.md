# Local Host and optional service

The independent MyGo resident owns keyboard and middle-button shortcuts for the main window, search, sequential paste and rich paste. `MButton` and `MouseMiddle` resolve to one exclusive local claim, with Host-side canonicalization and cross-action conflict checks. Windows installs its low-level mouse hook on a dedicated OS thread with its own message pump, independent of blocking resident UI work; X11 uses a checked passive button grab and waits on the display/cancellation descriptors without an idle polling timer. Both platforms deliver only on middle-button release; X11 filters button detail so other buttons during the grab cannot trigger the shortcut. Input delivery is bounded and posted outside the native callback, and stale deliveries are discarded after unregister. Linux honors `mouse_hotkey`/`all` in the existing service opt-out variables; native Wayland does not claim XWayland input as a global shortcut. The X11 fixtures verify middle-button wake after WebView destruction and rich HTML paste without creating a main renderer. Windows toggle/recreation is gated by the disposable desktop fixture.

`dzc-host` owns the same typed router, permissions, event buffer and capture lifecycle for an embedded process and `dzc-service`. It depends on Core, Platform and the opt-in offline Wire validator; it does not depend on Tauri, GTK, WebView or an HTTP client. Platform owns all IPC identity, ownership and process syscalls.

Nothing starts the service automatically. Desktop packages contain `dezirclip`, the independent `dzc` CLI and `dzc-service` once each. The shared preparation hook builds the latter two without desktop features and synchronizes their actual Cargo bundler inputs. Standalone CLI archives remain CLI-only; service startup requires a matching sibling helper installed by a desktop package.

```
dzc service start
dzc service status --json
dzc privacy on --seconds 300 --json
dzc privacy off
dzc service stop
```

Desktop handoffs can use `dzc service stop --from-instance <service-instance-id>`.
The controller compares this identity on the authenticated connection that sends
the stop request. A mismatched instance is rejected before lifecycle changes;
the command retains the ordinary stop acknowledgement and process-exit checks.

`dzc service restart-elevated --from-instance <service-instance-id> --database <absolute-database-path> --json` is
the Windows handoff operation for a helper that already passed UAC. It rejects
unelevated callers, verifies the matching standalone Service and packaged helper
before stopping anything, preserves capture mode, and confirms the replacement
is the exact newly spawned child. If another Host starts during the transition,
the operation fails instead of treating that process as its elevated replacement.
This command does not display UAC or launch the desktop interface itself.

MyGo's `restart_as_admin` asks Windows to run the same packaged desktop executable
with `runas`. Its helper verifies the original resident's executable and user,
passes the exact database from the authenticated desktop endpoint to the bundled
CLI, and performs the instance-bound Service restart. The replacement desktop
checks the new Host's identity and elevated token before acknowledging readiness.
It then waits on the original resident's process handle before opening its UI or
registering shortcuts. Cancellation before the helper starts keeps the original
Service and resident running. UAC is interactive and has no application timeout
that could report cancellation while leaving a live elevation request behind.

The disposable Windows CI handoff fixture invokes the helper in its already
elevated runner session. It verifies Service replacement, capture preservation,
waiting for the original resident and reopening the same history. That fixture
does not automate or claim to validate the interactive Windows consent dialog.

`start --no-capture` explicitly runs only the local query/privacy Host. Starting an existing service with a different capture mode is rejected. Startup checks the actual helper's version, schema, protocol and, for a verified checkout, build identity before asking an embedded Host to hand off. A newly spawned helper is accepted only when the authenticated peer PID equals that exact child. Failed startup terminates only that child. `stop` first acknowledges draining the capture listener and processor, then confirms listener closure and the service process's exit. Linux process-exit confirmation uses `pidfd_open` and therefore fails closed on kernels without that facility; the helper is not reported stopped on an unconfirmed exit.

Process-exit observation is preflighted before preparing an endpoint, stopping an embedded owner or launching a service. Missing kernel support or denied observation is reported as unavailable; ordinary CLI and embedded capture retain their existing kernel support. A regression uses a real embedded IPC endpoint and a denied probe to verify its instance remains live, no handoff occurs and no database/helper is opened.

The current user's protected control credential is generated after exclusive endpoint bind, is valid only in that Host instance and is removed only if its bytes remain unchanged. A hello's `client_role` never grants privileges. Delegated Surface/MCP grants have bounded lifetimes and permission ceilings and are checked again on every request; live connections lose access after revocation. Surface reads use restricted Core summaries and may request an authorized ordinary copy without receiving its body. MCP body access is limited to bounded ordinary text. External peers never obtain a Core permit or a private key.

Core owns durable history revision and privacy epoch. Each Host has a fresh instance ID and event sequence; its bounded event buffer reports gaps and requests a fresh snapshot. Events contain identifiers/status only. No idle event, timer or service worker is created in an ordinary CLI invocation.

An event long poll holds neither the mutation lock nor its execution permit. Revocation and shutdown interrupt existing waits, and a subscriber's grant is checked again before returning a result. Shutdown first stops accepting connections and interrupts idle or incomplete reads; requests with an already accepted complete frame retain their bounded dispatch and response write, including the stop/handoff acknowledgement. Only after those responses drain does the server release its remaining connection state. Native IPC regressions cover six concurrent subscriptions with privacy/revoke/stop requests and a deliberately paused stop/handoff acknowledgement while another connection finishes.

Windows capture ownership uses the actual user SID and token session. Linux deliberately uses one capture lease per UID across **all** graphical sessions: different `DISPLAY` screens, Wayland relative/absolute socket labels, data paths and aliases cannot create a second capturer. This conservative policy permits only one capture owner for a Linux user even when that user has several independent graphical sessions. Endpoint labels still separate connections and are not treated as OS-authenticated Linux session identity. UDS peer UID/PID and Windows peer SID/session/PID are checked by Platform.

Both the native callback and the Core processor hold the OS lease. A failed or timed-out stop retains ownership while a worker is alive, including when its Host is dropped. Native readiness, worker liveness and confirmed joining are separate facts. Capture reads use the original Core privacy ticket before reading a body, and queued frames retain that ticket through their real Core transaction.

Verification uses private synthetic profiles. `scripts/test-local-host.py` executes actual helper lifecycle/privacy/grant/revoke operations with `--no-capture`; `scripts/test-capture-lease.py` uses two real processes without opening any clipboard. Native capture integration is separately gated by a private graphical fixture. Foreign Windows-account/session delivery and actual Windows clipboard capture require disposable native acceptance; string-only negative tests do not establish those claims. Full desktop remote hydration, unique hotkey ownership, MCP routing and updater helper lifecycle are the following client-integration change.
